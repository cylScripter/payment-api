# 功能规格 — 商户 API_KEY 接口鉴权

**分支** `main` | **日期** 2026-11-17 | **状态** 规格已完成

**输入** “实现接口鉴权，要求 Authorization: Bearer ${API_KEY}，API_KEY 提供接口生成”

**用户补充** “这个鉴权是面向商户的”“仅 HTTP 业务接口鉴权，健康检查和支付回调豁免”

## 背景

商户需要使用系统生成的 API_KEY 访问 HTTP 业务接口，系统据此识别调用商户并限制其业务操作归属。
本功能明确商户密钥的签发和使用规则，健康检查及支付渠道回调按各自约定接入。

## 用户故事

### US1 - 为商户生成调用密钥（P1）

平台管理方通过生成接口为已存在的正常商户签发 API_KEY，并交付给该商户用于后续业务请求。

1. **Given** 平台管理方持有有效管理凭证且目标商户正常，**When** 指定商户账号请求生成 API_KEY，**Then** 获得一个绑定该商户、非空且可立即使用的新密钥。
2. **Given** 商户已有一把 API_KEY，**When** 平台再次为其成功生成密钥，**Then** 新旧密钥不同且均可独立使用。
3. **Given** 调用方缺少有效管理凭证，**When** 请求生成 API_KEY，**Then** 请求被拒绝且没有新密钥生效。
4. **Given** 商户还没有 API_KEY，**When** 平台使用有效管理凭证签发，**Then** 可以取得该商户的首把可用密钥。
5. **Given** 指定商户不存在或已禁用，**When** 请求生成 API_KEY，**Then** 返回明确错误且没有新密钥生效。

### US2 - 携带密钥访问业务接口（P1）

商户在 HTTP 请求中携带有效 API_KEY，完成登录信息交换、支付下单等受保护的业务操作。

1. **Given** 商户持有系统签发给自己的有效 API_KEY，**When** 使用 `Authorization: Bearer ${API_KEY}` 发起符合业务要求且商户账号匹配的请求，**Then** 请求以该密钥所属商户的身份进入业务处理流程。
2. **Given** 请求缺少凭证、凭证格式错误或密钥未知，**When** 访问任一受保护接口，**Then** 返回未认证结果且没有业务操作发生。
3. **Given** 调用方持有有效 API_KEY，**When** 请求业务参数错误，**Then** 返回原有业务参数错误。
4. **Given** 已成功签发 API_KEY，**When** 服务重启后再次携带该密钥请求，**Then** 密钥仍可通过鉴权。
5. **Given** 请求使用商户 A 的 API_KEY，**When** 请求中的 `merchant_account` 指定商户 B，**Then** 返回 403 且没有业务操作发生。
6. **Given** 正常商户持有有效 API_KEY，**When** 请求的业务契约不含商户账号，**Then** 系统仍能识别密钥所属商户并完成身份校验。
7. **Given** 密钥所属商户不存在或已禁用，**When** 使用该密钥请求受保护接口，**Then** 返回 401 且没有业务操作发生。

### US3 - 探活与支付通知正常接入（P2）

运维系统能够探测服务状态，支付渠道能够按既有回调约定发送支付结果。

1. **Given** 探活请求没有 API_KEY，**When** 调用健康检查，**Then** 返回现有健康检查结果。
2. **Given** 支付渠道发送符合既有校验规则的回调，**When** 请求没有 API_KEY，**Then** 回调仍按渠道约定处理和应答。
3. **Given** 支付回调未通过既有校验，**When** 发送回调请求，**Then** 仍按原有规则拒绝该回调。

## 功能需求

- **FR-1** 系统必须提供按商户账号生成 API_KEY 的 HTTP 接口，成功时返回一个新的完整密钥及所属商户账号。失败时必须返回明确错误，且不得返回可被误认为已经生效的密钥。
- **FR-2** 生成接口必须使用独立的平台管理凭证授权，普通商户 API_KEY 调用生成接口时返回 403，管理凭证缺失或错误时返回 401。平台可为尚无 API_KEY 的商户签发首把密钥。此签发授权方式为默认假设。
- **FR-3** 每次成功签发的 API_KEY 必须非空、不可预测且与其他有效密钥不同。新密钥必须在成功响应后立即可用于业务鉴权。
- **FR-4** 受保护 HTTP 接口必须通过请求头 `Authorization: Bearer ${API_KEY}` 接收凭证，校验完整密钥。认证方案名称大小写不敏感，密钥值大小写敏感。
- **FR-5** 鉴权覆盖 HTTP 业务接口。健康检查和支付渠道回调豁免 API_KEY 校验，生成接口使用 FR-2 的管理凭证授权。
- **FR-6** 现有及新增 HTTP 业务接口默认要求有效商户 API_KEY，包括微信登录信息交换和支付下单。支付回调继续按既有渠道规则校验和应答。
- **FR-7** 凭证缺失、密钥为空、认证方案错误、凭证存在多个值或密钥未知时，系统必须在业务处理前拒绝请求。HTTP 返回 401，并沿用现有 `code`、`message`、`data` 响应格式。
- **FR-8** 每把 API_KEY 必须唯一归属一个商户。系统必须根据密钥识别商户身份，业务请求含 `merchant_account` 时必须与密钥所属商户账号完全一致，不一致时返回 403 且拒绝业务处理。启用商户参数校验的接口必须显式提供商户账号，缺失或无效时返回 400。
- **FR-9** 校验凭证或商户身份的依赖不可用时，受保护请求必须返回 HTTP 503，请求不得进入业务处理。
- **FR-10** 成功签发的密钥必须支持后续重复请求、服务重启及同一部署内不同服务实例的校验。再次生成密钥必须保留已有密钥的有效性。
- **FR-11** 完整 API_KEY 仅通过成功签发响应交付，日志、错误信息和普通业务响应必须避免输出完整密钥。
- **FR-12** 鉴权通过后，现有业务请求字段、响应字段、字段编号及金额约定继续适用。现有调用方访问受保护接口时必须新增凭证，否则按 FR-7 拒绝请求。
- **FR-13** 系统仅为已存在且状态正常的商户签发 API_KEY。签发失败统一返回 503。业务请求校验时，密钥所属商户不存在或已禁用均返回 401。

### 关键实体

- **商户** 已存在的业务主体，以商户账号标识，具备正常或禁用状态。
- **API_KEY** 绑定一个商户的业务访问凭证，具备唯一值、所属商户和签发时间，可在多次请求中使用。
- **受保护请求** 访问鉴权覆盖范围内业务能力的请求，在执行业务操作前必须通过凭证校验。
- **密钥签发者** 持有独立管理凭证、可为指定商户签发密钥的平台管理方。

### 假设与依赖

- API_KEY 绑定现有商户账号，商户身份及业务归属采用同一账号判断。
- API_KEY 默认长期有效，重复签发产生额外可用密钥。
- 健康检查与支付渠道回调豁免 API_KEY 校验，支付回调继续使用现有渠道校验规则。
- 用户已明确商户身份及 HTTP 鉴权范围。生成接口默认由平台管理方持独立管理凭证调用，为指定商户签发密钥，具体管理凭证接入方式在规划阶段确定。
- 调用方需要取得并保存密钥，在业务请求中携带凭证。上线验收需要具备可使用的密钥及既有业务依赖环境。

## 边界情况

- `Authorization` 缺失、只有 `Bearer`、密钥为空或认证方案错误时，统一按未认证处理。
- 重复的 `Authorization` 请求头、多个凭证值或一个值中拼接多把密钥时，拒绝请求。
- 将密钥放在查询参数或请求体中，且没有符合要求的认证请求头时，按凭证缺失处理。
- 请求携带格式正确但未知的密钥时，拒绝请求，错误信息避免回显密钥或披露其他密钥信息。
- 商户 A 的密钥与商户 B 的账号组合请求时，返回 403，不得为商户 B 下单或返回其业务数据。
- 目标商户账号为空时，生成接口返回 400。业务接口仍按原有契约校验商户账号是否必填。
- 同一商户多把密钥、不同商户同时签发密钥时，每把密钥均保持唯一且归属正确。
- 多个生成请求并发成功时，每个请求均获得独立有效密钥。
- 生成请求失败或客户端未收到成功响应时，调用方可重新生成一把密钥，后续成功签发不影响之前有效密钥。
- 凭证校验依赖不可用时，拒绝受保护业务访问，健康检查和回调继续按各自规则处理。

## 不在本次范围

- gRPC 接口鉴权。
- 商户注册、用户会话、角色权限及更细粒度的商户内部权限管理。
- 密钥列表、明文找回、主动吊销、自动到期和定期轮换能力。
- 业务金额、订单处理流程及支付渠道回调协议的调整。

## 验收标准

- [ ] **SC-1** 平台为已存在的正常商户签发首把 API_KEY 后，该商户能使用密钥完成一次属于自己的业务操作，整个流程无需人工编辑密钥记录。
- [ ] **SC-2** 对所有纳入范围的业务入口，使用有效密钥的验收请求均通过鉴权，缺失、空值、错误方案、多值和未知密钥的请求均被拒绝，覆盖率达到 100%。
- [ ] **SC-3** 所有被鉴权或商户归属校验拒绝的验收请求产生的新增订单及其他业务写入数量均为 0。
- [ ] **SC-4** 连续成功生成 100 把密钥后，100 把密钥各不相同且全部可用，首把密钥仍可用。重启服务并切换到同一部署内另一实例后，抽验密钥均可继续使用。
- [ ] **SC-5** 无 API_KEY 的健康检查、有效支付回调及无效支付回调验收场景，均得到符合原有规则的结果。
- [ ] **SC-6** 未获签发授权的生成请求全部被拒绝，调用方可从错误结果识别请求失败，且没有新密钥生效。
- [ ] **SC-7** 验收过程中，完整密钥出现在成功签发响应之外的日志、错误信息及普通业务响应中的次数为 0。
- [ ] **SC-8** 使用商户 A 的密钥携带商户 B 的账号访问业务的验收请求全部被拒绝。使用各自密钥和匹配账号的请求全部通过身份校验，跨商户越权成功次数为 0。
- [ ] **SC-9** 商户不存在或已禁用的密钥签发和业务访问场景全部被拒绝，符合 FR-13 的结果约定。
