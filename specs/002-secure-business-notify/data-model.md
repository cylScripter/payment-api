# 数据模型 — 商户支付回调签名

**规格** [spec.md](spec.md) | **计划** [plan.md](plan.md)

## 商户回调密钥

商户表 `pay_merchant` 增加以下字段。

| 属性      | 定义                                                           |
|---------|--------------------------------------------------------------|
| 字段名     | `notify_secret`                                              |
| 存储类型    | `VARCHAR(512) NOT NULL DEFAULT ''`                           |
| Go 属性   | `NotifySecret string`                                        |
| GORM 标签 | `column:notify_secret;type:varchar(512);not null;default:''` |
| JSON 标签 | `-`                                                          |
| 保存内容    | `EncryptPEMString` 生成的 `v1:` 格式密文                            |
| 关联方式    | 现有商户记录的 `id` 和 `account`                                     |

密钥明文由现有 `GenerateSecret` 生成，为 16 个安全随机字节的 32 字符十六进制表示。HMAC 直接使用该字符串的 UTF-8 字节。现有字符串加密工具返回的密文可由所规划字段容量容纳。

密钥分配保留商户身份、通知地址与现有状态。初始化操作从主库定位商户记录，再以该记录主键执行条件更新。最终用于交付的密钥来自主库读回的保存值。

### 状态变化

| 当前状态        | 操作        | 结果                    |
|-------------|-----------|-----------------------|
| 空字符串        | 首次初始化成功   | 保存密文并向授权操作者交付对应明文     |
| 已保存密文       | 重复初始化     | 解密并交付已保存密钥            |
| 并发初始化空字段    | 同时生成候选值   | 首次成功条件更新生效，各调用读回同一保存值 |
| 保存成功但命令应答丢失 | 重新执行命令    | 取得已保存密钥               |
| 保存值无法解密     | 命令执行或通知投递 | 返回可排查错误，原密文保留         |
| 密钥为空        | 通知投递      | 投递失败，保留待通知状态          |

## 通知报文与验证信息

`BusinessNotify` 沿用当前业务字段，签名过程使用一次 `json.Marshal(payload)` 得到的原始字节。完整字段定义见 [回调契约](contracts/business-notify.md)。

| 信息        | 保存位置                 | 含义                          |
|-----------|----------------------|-----------------------------|
| 业务订单与支付结果 | 现有 `pay_order` 和发送报文 | 支付单号、业务订单号、金额和支付时间等         |
| 通知时间      | `X-Pay-Timestamp`    | 每次发送时取得的当前秒级时间              |
| 验证凭证      | `X-Pay-Signature`    | `v1=` 加 HMAC-SHA256 小写十六进制值 |
| 回调密钥明文    | 分配结果及发送期间的局部变量       | 商户后端验签与支付服务签名               |

签名头在每次实际发送时计算。支付成功时间 `pay_time` 继续表示渠道确认的交易时间。

## 通知投递状态

复用 `pay_order.business_notify_status`。

1. `NotifyBusiness` 将本次业务通知置为 `PENDING`。
2. 取得商户密钥并解密、生成原始报文及签名，发送通知。
3. HTTP 2xx 应答后更新为 `SUCCESS`。
4. 密钥、解密、序列化、网络或非成功应答导致投递失败时保留 `PENDING`。

业务通知的失败通过现有通知错误路径记录，已确认的支付状态继续为 `SUCCESS`。商户端以 `out_trade_no` 约束发货或入账的幂等结果，验收涵盖并发通知。

## 数据访问与迁移

- 在现有 `MerchantMysql` 中新增密钥初始化所需读写方法，新增请求类型采用现有 option 构造习惯，读写沿用传入上下文。
- 初始化和通知配置读取使用主库。密文字段的 JSON 排除标签适用于 `Auth.GenerateAPIKey` 与 `syncAPIKeys` 对商户对象的序列化。
- 新库结构同步到 `migrations/init.sql`，已有数据库使用 `migrations/20261118_merchant_notify_secret.sql` 增加字段。
- 存量记录初值为空，由受控本地命令逐商户初始化，并向商户交付对应明文。
- 字段部署、商户密钥准备及接收端验签部署完成后，再部署发送签名代码。
