# 商户支付回调签名调研

**日期** 2026-11-18 | **规格** [spec.md](spec.md)

## 1. 回调密钥的保存与分配

**决策** 在 `pay_merchant` 增加 `notify_secret` 密文字段，模型使用 `json:"-"`。提供本地命令 `go run ./cmd/notify-secret -account <商户账号>`，完成密钥初始化和受控交付。再次执行返回该商户已保存密钥的解密结果。

**依据** 当前商户记录已经持有业务通知地址，`WechatNotifier.LoadConfig` 按账号读取该记录。现有 `helpers.GenerateSecret` 返回由安全随机字节生成的 32 字符十六进制字符串，可直接用于本功能。`EncryptPEMString`、`DecryptPEMString` 接受普通字符串，可复用 `config.Get().EncryptKey` 对其加解密。模型的 JSON 排除标签使商户鉴权缓存的序列化结果保持对密钥的隔离。

**评估过的路径** 现有 API Key 接口扩展、独立密钥接口、本地命令。现有管理路由中的管理鉴权为注释状态，本地命令可通过运维主机权限及现有商户交付流程提供所需能力。命令仅初始化配置和数据库连接，输出给调用方的明文属于受控交付结果。

**现成能力与缺口** `internal/pkg/helpers/crypto.go` 已具备随机密钥和加解密能力。需要补充商户字段持久化和单个商户的分配命令。`internal/repo/merchant.go` 作为现有商户数据库入口复用。

## 2. 重复初始化与存量商户

**决策** 读取主库商户记录，已有密文时复用。首次保存采用商户主键及 `notify_secret = ''` 条件更新，再读取主库最终值。并发执行返回实际保存的同一密钥，失败结果交由调用方重试。新字段默认空字符串，存量商户通过同一命令初始化。

**依据** 条件更新可将一条商户记录从未配置推进到已配置。通知密钥与 API Key 分开管理，重复分配操作必须保留正在使用的回调密钥。通知读取商户配置时传入调用方上下文并从主库读取，以便初始化成功后的通知取得已保存密钥。

**评估过的路径** 首次通知自动生成、重复执行覆盖、条件初始化。初始化命令能先完成密钥交付，再由商户准备验签。条件初始化满足并发与重试的一致性要求，沿用现有数据访问方式。

## 3. 签名的最小集成位置

**决策** 将发送方法参数调整为 `sendBusinessNotify(ctx, merchant, payload)`，使用商户对象承载通知地址和密文密钥。方法内解密、序列化一次、按当前秒级时间签名并发送同一份请求体。直接使用 Go 标准库 `crypto/hmac`、`crypto/sha256` 和 `encoding/hex`。

**依据** 当前发送函数只有 `WechatNotifier.NotifyBusiness` 一个直接调用方，调用方已持有 `n.merchant`。方法仍为三个参数。现有 `bytes.NewReader(body)` 可继续发送签名覆盖的原始字节。标准库提供签名及常量时间比较能力。[Go HMAC 文档](https://pkg.go.dev/crypto/hmac)、[Go SHA256 文档](https://pkg.go.dev/crypto/sha256)、[Go hex 文档](https://pkg.go.dev/encoding/hex)

**评估过的路径** 额外签名接口、独立签名服务、发送方法内直接签名。当前调用范围适合在发送方法中完成这一协议步骤。

## 4. 验签与时间窗口

**决策** 保留用户指定的 `v1` 协议。HMAC key 为密钥字符串 UTF-8 字节，输出小写十六进制。商户先校验时间与签名，使用解码后的签名字节调用 `hmac.Equal`，随后解析业务内容。时间条件为 `timestamp < now-300 || timestamp > now+300` 时拒绝。

**依据** 原始字节直接参与签名，报文格式变化会改变签名。时间条件直接覆盖前后边界，业务幂等按支付单号实现。新投递读取当前时间后重新计算签名，同一秒内的相同报文允许得到相同签名。[Go HMAC 比较说明](https://pkg.go.dev/crypto/hmac#Equal)

**评估过的路径** JSON 解析后重新编码验签、原始报文验签。用户已明确原始字节契约，商户通过对接文档和联调完成接收端实现。

## 5. 状态与验证方式

**决策** 复用现有先置 `PENDING`、发送成功后置 `SUCCESS` 的通知流程。缺密钥或解密失败作为简单投递错误返回。验证采用构建、静态检查、固定向量核对及商户测试接收端联调。

**依据** `NotifyBusiness` 已在发送前更新待通知状态，投递失败保留原支付成功结果。当前定时补发函数为空，重新签名行为由每次实际发送时计算实现。商户端的串行及并发幂等通过其接收端的业务结果验收。

**评估过的路径** 纯向量核对、实际发送捕获与商户联调。向量验证字节约定，实际发送捕获验证发送函数使用真实商户密钥及相同请求体，商户联调验证时效和业务幂等。
