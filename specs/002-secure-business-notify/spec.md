# 功能规格 — 商户支付回调签名

**分支** `main` | **日期** 2026-11-18 | **状态** 规格已完成

**输入** 用户明确要求为每个商户分配独立的 `notify_secret`，双方后端保存，支付服务加密存储；回调携带 `X-Pay-Timestamp` 和 `X-Pay-Signature`，按指定的 HMAC-SHA256 规则签名原始请求体；商户校验 5 分钟时间窗口、验证签名、核对订单并按 `out_trade_no` 幂等处理，每次重新投递时重新计算时间戳和签名。

## 背景

支付服务目前将支付成功业务报文直接发送给商户。商户需要验证通知来源、内容完整性和时效，核对订单后再发货或入账，并通过支付单幂等处理避免重复通知造成重复业务效果。

## 用户故事

### US1 - 取得独立回调密钥并验证通知（P1）

支付服务为每个商户分配独立回调密钥，商户后端使用该密钥验证收到的支付结果。

1. **Given** 商户已分配回调密钥，**When** 支付服务保存密钥并交付商户后端，**Then** 支付服务中的密钥获得加密存储，双方可用于同一商户的通知签名与验签。
2. **Given** 商户 A、B 持有各自独立密钥，**When** 使用商户 B 的密钥验证商户 A 的通知，**Then** 验签失败。
3. **Given** 商户存在可用回调密钥，**When** 支付服务发送支付成功通知，**Then** 通知携带约定的时间戳和签名，签名覆盖实际发送的完整原始报文。
4. **Given** 支付服务无法取得商户的可用回调密钥，**When** 尝试生成通知签名，**Then** 本次投递返回失败，商户收到的未签名通知数量为 0。

### US2 - 拒绝篡改或过期的通知（P1）

商户读取原始请求体，校验时间戳和签名，通过后解析业务内容并核对订单。

1. **Given** 通知使用商户密钥签名且时间有效，**When** 商户按约定验证收到的原始报文，**Then** 验签通过，可以继续核对商户账号、订单号和金额。
2. **Given** 一份有效通知，**When** 原始报文或时间戳被修改后继续使用原签名，**Then** 验签失败且业务处理次数为 0。
3. **Given** 通知时间与商户当前时间相差超过 5 分钟，**When** 商户验证通知，**Then** 通知被拒绝且业务处理次数为 0。
4. **Given** 签名有效且时间有效，**When** 商户账号、订单号或金额与业务订单不匹配，**Then** 商户拒绝处理该支付结果。

### US3 - 幂等处理重复通知和重新投递（P1）

商户按支付单号处理同一支付结果，支付服务重新投递时按本次投递时间重新签名。

1. **Given** 某支付单已经处理成功，**When** 商户再次收到该支付单的有效通知，**Then** 返回成功应答且业务效果累计为一次。
2. **Given** 同一支付单的有效通知并发到达，**When** 商户处理这些通知，**Then** 对应业务效果累计为一次。
3. **Given** 原通知已超过有效时间窗口，**When** 支付服务再次投递同一支付结果，**Then** 使用本次投递的当前时间重新生成签名，商户可在新的有效时间内完成验证。
4. **Given** 商户已完成验签、订单核对和业务处理，**When** 应答本次通知，**Then** 返回 HTTP `200` 或 `204`。

## 功能需求

- **FR-1** 支付服务必须为每个商户分配独立、不可预测的回调密钥 `notify_secret`，双方后端保存，支付服务加密存储。该密钥独立于商户访问支付服务使用的 API Key。
- **FR-2** 支付服务发送业务通知时，必须使用该通知所属商户的回调密钥生成签名。无法取得可用密钥或无法完成签名时，本次投递返回失败。
- **FR-3** 回调必须携带 `Content-Type: application/json`、`X-Pay-Timestamp` 和 `X-Pay-Signature`。时间戳表示本次投递的秒级 Unix 时间，签名格式为 `v1=<签名的十六进制字符串>`。
- **FR-4** 待签名内容必须按下述约定拼接。通知发送方签名和商户验签必须使用相同版本、时间戳文本、密钥及原始请求体字节。
- **FR-5** 支付服务必须直接对 `json.Marshal(payload)` 得到的原始字节签名，并发送同一份字节作为请求体。商户必须使用收到的原始请求体完成验签，再解析 JSON。
- **FR-6** 商户必须校验通知时间与当前时间的绝对差值，差值不超过 300 秒时满足时效要求，超过 300 秒时拒绝处理。缺少或无法识别的时间戳应作为验证失败处理。
- **FR-7** 商户必须使用自己的回调密钥计算签名，将收到的十六进制签名解码为字节，并通过 `hmac.Equal` 比较。凭证缺失、格式错误、版本不支持或签名不匹配时拒绝业务处理。
- **FR-8** 商户必须在时间戳和签名校验通过后解析业务内容，核对商户账号、订单号和金额。业务信息不匹配时拒绝处理。
- **FR-9** 商户必须按 `out_trade_no` 幂等处理同一支付结果，串行或并发重复通知均只产生一次对应业务效果。处理成功及已处理成功的有效重复通知返回 HTTP `200` 或 `204`。
- **FR-10** 支付服务每次重新投递时必须读取本次投递的当前时间，并重新计算签名。同一支付结果通过原支付单号关联，支付成功时间仍表示原交易时间。
- **FR-11** 回调新增签名请求头，现有业务报文继续使用原字段名及含义。下单 `amount` 以元计，回调 `total_amount`、`pay_amount` 以整数分计。
- **FR-12** 商户对接文档必须补充回调密钥使用方式、请求头、完整签名规则、时间窗口、原始请求体验签、业务核对、幂等处理和成功应答约定，并提供可核对的签名示例。

### 用户指定的回调协议

回调请求头如下。

```http
Content-Type: application/json
X-Pay-Timestamp: 1794967200
X-Pay-Signature: v1=<签名的十六进制字符串>
```

签名规则如下，`\n` 表示单个换行字节，末尾换行参与签名。

```text
待签名内容 = "v1\n" + timestamp + "\n" + 原始请求体 + "\n"
signature = hex(HMAC-SHA256(notify_secret, 待签名内容))
```

`timestamp` 使用 `X-Pay-Timestamp` 中的原始十进制文本。密钥使用双方保存的 `notify_secret` 字符串的 UTF-8 字节，签名输出约定为 64 个小写十六进制字符。时间戳与报文均采用实际传输值。

### 关键实体

- **商户回调密钥** 商户独立的 `notify_secret`，供支付服务签名和商户后端验签，支付服务中的持久化内容为密文。
- **支付成功业务通知** 包含支付单号、业务订单号、商户账号、金额、支付状态等现有业务内容的原始报文。
- **通知验证信息** 本次投递的时间戳和带 `v1` 版本标识的签名，与该次原始报文绑定。

### 假设与依赖

- 本规格采用用户本轮明确给出的回调签名协议，功能范围限定为密钥分配与加密保存、通知签名和商户接入约定。
- 默认以秒级 Unix 时间、64 位小写十六进制签名和密钥字符串的 UTF-8 字节作为双方一致的编码约定。
- 密钥交付沿用平台与商户的现有后端接入流程，具体分配入口和保存位置在规划阶段确定。
- 平台与商户维护准确时钟，时间窗口限制旧通知的有效期，窗口内重复业务效果通过支付单幂等处理约束。
- 商户接收端由商户维护，验签与业务处理要求通过商户对接文档及联调落实。
- 重新投递沿用已有投递入口，本规格约定每次投递的签名行为。

## 边界情况

- 不同商户之间使用错误的回调密钥时，验签失败。
- 请求体中的金额、订单号、商户账号、状态或空白被改动时，原签名验证失败。
- 时间戳被修改后继续使用原签名时，验签失败。
- 通知时间比当前时间早或晚恰好 300 秒时满足时效要求，早或晚 301 秒时拒绝处理。
- 缺少签名头、签名格式错误或时间戳无法识别时，拒绝业务处理。
- 签名和时间戳均有效，但订单归属或总金额核对失败时，拒绝业务处理。
- 同一支付结果在有效时间窗口内重复到达时，业务效果累计为一次，处理成功后返回成功应答。
- 商户处理成功后应答丢失，再次收到该支付单的有效通知时返回成功应答。
- 原通知过期后重新投递时，采用重新投递时的当前时间生成签名，商户依据新的通知时间校验时效。

## 不在本次范围

- 回调密钥管理门户、自动轮换及多密钥并行管理。
- 回调安全模式开关、通知调度和自动补发能力。
- 商户接收端应用的直接修改和部署。

## 验收标准

- **SC-1** 两个商户均可取得独立回调密钥，支付服务中可直接读取的完整明文密钥记录为 0，两个商户各自的有效通知验证通过率为 100%，交叉使用密钥时通过次数为 0。
- **SC-2** 对给定密钥、时间和原始业务报文，发送方与接收方得到一致的验证结果，全部约定示例均可复现。
- **SC-3** 覆盖报文篡改、时间戳篡改、凭证缺失、格式错误及签名不匹配的验收场景，错误通知导致的业务处理次数为 0。
- **SC-4** 对通知时间与当前时间前后各相差 300 秒和 301 秒的验收场景，时效判断结果 100% 符合 FR-6。
- **SC-5** 同一支付结果串行投递 10 次和并发投递 10 次时，每种场景的业务效果累计均为一次，已成功处理的有效重复通知均收到成功应答。
- **SC-6** 原通知过期后重新投递的验收场景均使用本次投递时间重新签名，并在新的有效时间内验证通过。
- **SC-7** 商户账号、订单号或金额不匹配的通知，以及缺少可用密钥的投递场景，分别满足业务处理次数为 0、未签名通知送达次数为 0。
- **SC-8** 商户根据文档完成有效通知、无效通知、过期通知及重复通知联调，全部示例均有明确预期结果，订单关联及金额核对结果符合既有业务含义。
