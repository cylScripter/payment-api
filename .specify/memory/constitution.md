# payment-api宪章

## 核心原则

### I. 模块职责与分层

- HTTP 请求接收、参数绑定及应答处理放在 controller，业务逻辑放在 service，
  数据库操作放在 repo，模型及数据库入口放在 models。
- HTTP 与 RPC 必须复用 service。HTTP 路由在 router 显式注册，RPC 服务在 rpc 注册。
- 渠道 SDK 封装、回调解析器和公共组件放在 pkg；组件初始化与关闭统一接入 initials。
  配置加载及热更新由 config 管理。
- 文件归属必须遵循下方项目结构，使业务流程、协议接入和基础组件具有明确维护位置。

### II. 接口契约与兼容性

- 接口以 `.proto` 为源，修改后执行 `make proto` 同步生成代码。service 优先复用
  已有的 proto 请求和响应类型。
- 必须保持已有字段编号、JSON 字段名和调用行为的兼容性。需求涉及契约调整时，
  必须说明对现有调用方的影响。
- 普通 HTTP 接口沿用 `code`、`message`、`data` 响应格式及 `protojson` 序列化。
  支付渠道回调必须按对应渠道的应答协议返回。
- service 错误沿用 gRPC `codes` 和 `status`；数据库及外部请求必须传递调用方的
  `context.Context`，HTTP 入口使用 `ctx.Request.Context()`。

### III. 简单实现与现成 API 复用

- 实现代码时必须加载并应用 `engineering-suite-ponytail:ponytail` 技能，默认使用 `full` 强度，
  用户指定强度时按其要求执行。理解需求与现有调用流程后，按技能要求检查需求必要性、
  现成能力与最小可用实现，将改动限制在完成当前需求所需的范围。
- 代码必须以简洁为主，所有逻辑从满足当前需求的最简单可用实现开始，先写清晰、直接的处理流程。
  通过明确职责和依赖降低代码耦合度，随实际业务需求逐步演进，使代码容易理解、修改、验证和扩展。
- 实现必须围绕当前需求，优先复用现有逻辑、类型、依赖和调用方式，遵循所在模块的代码风格。
- 实现前必须查找项目、相关服务、Go 标准库及已有依赖提供的现成 API，核对其功能、
  参数、返回值和调用约束。现成 API 能满足当前需求时必须直接复用，避免重复实现相同能力。
- 新增实现必须基于现成 API 无法满足的具体需求，并在方案或交付说明中记录能力缺口。
  复用时沿用已有调用方式，仅按当前需求补充必要适配。
- 编码前明确输入、输出、结构体职责和调用流程。设计模式仅在解决当前明确问题时引入。
  按职责组织方法，避免单个函数堆积大量业务逻辑。
- 函数和方法的参数一般不超过 3 个。复杂参数构造采用项目已有的 option 模式。
- 根据实际职责组织结构体和方法。出现实际复用需求、已确认的业务差异或明确的性能问题时，
  再增加所需接口、抽象和扩展点，减少接口断言。不得为尚未确认的需求预建通用框架。
- 少定义辅助函数，避免机械拆分 `normalizePage`、`encodeCursor`、`decodeCursor`、`postDTO` 等函数。
- 禁止过度参数校验，额外参数校验在用户明确说明必要性后添加，省略 `req == nil` 判断。
- 禁止过度防御。异常处理必须围绕当前明确需求，避免重复检查和基于假设性异常堆叠兜底分支，
  保持已有显式忽略 error 的写法。
- 命名必须简短且能准确表达语意，沿用所在模块的惯用名称。
- 修改过的 Go 文件必须使用 `gofmt`。结构体初始化时每个字段单独占一行。

### IV. 数据模型与数据库访问

- 数据模型字段必须添加明确的 `gorm` 标签，表模型必须提供 `TableName()` 方法。
- 数据库访问使用持有私有字段 `db *gorm.DB` 的 `MySQLXxx` 对象，
  通过 `NewMySQLXxx(db)` 构造。
- 查询条件必须使用 `ReqXxx` 结构体，字段保持私有，通过 Functional Options 构造。
- 查询请求构造器签名为 `NewReqXxx(opts ...func(*ReqXxx)) ReqXxx`。
- 单字段选项遵循 `WithReqXxxBrandCode(brandCode string) func(*ReqXxx)` 的形式。
- 分页选项遵循 `WithReqXxxPage(page, size int32) func(*ReqXxx)` 的形式。
- 禁止过度使用事务，新增事务在用户明确说明必要性后引入。

### V. 业务解耦与职责划分

- 业务实现前必须梳理完整调用流程，明确各步骤的输入、输出、状态变化、依赖及职责归属，
  再确定方法、结构体和模块的组织方式。
- 主流程必须清晰编排业务步骤。校验、规则计算、状态更新、持久化和外部交互按各自职责
  放入对应的方法、对象或已有模块。
- 同一函数包含多个可独立描述、独立变化的业务步骤时，必须按职责拆分。
  随需求增加业务步骤时，必须重新检查函数职责和嵌套结构，再继续实现。
- 数据库、渠道 SDK、协议接入和业务规则之间的依赖必须遵循现有分层。
  跨模块通过明确的调用入口协作，使单项规则或外部依赖的修改与扩展集中在所属模块，
  减少对无关模块的改动。
- 拆分粒度必须依据业务职责和变化原因。提取的方法必须具有明确语义和独立维护价值，
  主流程的执行顺序、错误返回和状态变化必须容易追踪。
- 职责拆分必须保留已有事务边界、幂等语义和 `context.Context` 传递，
  并沿用项目已有的构造方式。接口、设计模式和扩展点按当前已确认的需求引入。

接口由 Protobuf 定义，数据库访问使用 GORM 和 MySQL。

## 开发流程与验证

1. 开始修改前查看 `git status`、相关模块和同类实现，保留用户已有修改，确认本次需求范围。
2. 实现代码前加载 Ponytail 技能。业务编码前按原则 V 梳理调用流程、职责边界、状态变化及
   依赖方向，确认现有逻辑的复用位置和业务步骤的拆分方式。按原则 III 查找并核对现成 API，
   确定复用入口及确需新增的能力。
3. 修改代码符号前按项目协作约定完成影响分析。新增接口同步处理 proto、controller、service
   及相应路由或 RPC 注册，数据库变更同步模型和迁移 SQL。
4. 按改动范围执行 `go build ./...`、`go vet ./...`，按需运行现有测试。
   无特殊需求时不新增 `xxx_test.go`。文档改动核对目录、命令和实际代码。
5. 交付审阅必须检查函数职责、业务步骤拆分、依赖方向和现成 API、已有逻辑的复用情况，
   核实新增实现具有明确的能力缺口依据，消除重复实现。
   必须检查额外参数校验与新增事务符合用户明确要求，消除重复检查和假设性防御分支，
   确认实现简洁、职责清晰，业务扩展集中在相关模块。
   交付时说明实际改动、所采用的必要假设、验证结果和仍待完成或联调的事项。
   提交前按项目协作约定检查变更范围。
